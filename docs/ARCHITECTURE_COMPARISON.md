# Сравнение архитектур и выбор решения

Задача: телефон A («пульт») удалённо заставляет телефон B («приёмник») позвонить на номер шлагбаума через интернет, в том числе при заблокированном экране B. Ниже — три варианта, сравнение и обоснованный выбор.

Контекст из анализа оригинала: рабочая схема уже существует и использует **свой Parse Server + FCM data-push + самоуправляемый вызов**. Это важный аргумент — проверенный в бою эталон.

---

## Вариант A. Облачный сервер + push (FCM)

Телефон A → HTTPS → сервер (проверка прав, поиск привязки, дедуп) → FCM data-push → телефон B → звонок. Статусы операции A видит через сервер (polling или realtime).

**Нужно:** backend API, БД (устройства, привязки, очередь команд, результаты), регистрация/привязка устройств, FCM, хранение состояния, дедуп и повторы, защита API.

- **Надёжность:** высокая. FCM с `priority=high` будит приложение из Doze; сервер — источник истины, при недоставке повторяет.
- **Фон/локскрин:** работает — приём через `FirebaseMessagingService`, звонок через foreground-сервис `phoneCall`.
- **Стоимость:** FCM бесплатен. Хостинг — бесплатный тариф (Render/Fly/Railway free, или своя VPS ~$0–5/мес).
- **Минусы:** нужен серверный компонент; доставка push зависит от Google Play Services (на устройствах без GMS — не работает).

## Вариант B. Прямое соединение устройств (P2P)

Телефон A ↔ телефон B напрямую (WebRTC DataChannel / постоянный сокет).

- **NAT:** мобильные сети почти всегда за CGNAT → прямое соединение невозможно без STUN/TURN; TURN — это всё равно сервер (и трафик-ретранслятор, дороже).
- **Фон/локскрин:** телефон B должен держать постоянное соединение в фоне → либо вечный foreground-сервис (агрессивно убивается OEM-лаунчерами, жрёт батарею), либо всё равно FCM для «пробуждения». То есть «без сервера» не получается.
- **Надёжность:** низкая на мобильных сетях; переподключения, расход батареи, нестабильно при смене сети.
- **Вывод:** выбирать P2P только ради отсутствия сервера нельзя — он ухудшает надёжность. **Отклонено.**

## Вариант C. Минимальный управляемый backend + push (рекомендуется)

Небольшой backend: регистрация двух устройств, привязка (paired), **очередь команд как источник истины**, проверка прав, хранение результатов. Доставка — FCM data-push (как в оригинале). Если push не дошёл — B при старте/периодически забирает незавершённые команды из очереди (fallback pull). Статусы A видит опросом статуса команды (или SSE).

Отличие от A — акцент на **очереди-источнике истины** и fallback-pull, что закрывает «push не доставлен / B был офлайн».

- **Надёжность:** высокая, с деградацией: push (быстро) + pull (гарантия доставки после пробуждения).
- **Фон/локскрин:** как A.
- **Стоимость:** как A, бесплатный тариф достаточно для прототипа.
- **Безопасность:** авторизация устройств по токену, серверная проверка прав, номер не покидает B.

---

## Сводное сравнение

| Критерий | A (сервер+push) | B (P2P) | **C (мин. сервер+очередь+push)** |
|---|---|---|---|
| Сложность | средняя | высокая | **средняя** |
| Стоимость (прототип) | бесплатно | TURN платно/сложно | **бесплатно** |
| Надёжность доставки | высокая | низкая | **высшая (push+pull)** |
| Работа при офлайн B, затем онлайн | команда может потеряться | — | **доставится при пробуждении** |
| Локскрин/фон | да | хрупко | **да** |
| Безопасность | хорошая | сложнее | **хорошая** |
| Совместимость с Android/OEM | хорошая | плохая | **хорошая** |
| Развёртывание | простое | сложное | **простое** |

## Решение: **Вариант C**

Почему сервер вообще нужен (обоснование из ТЗ п. 5): требуется проверять права (кто кому разрешил звонить), дедуплицировать команды, переживать офлайн приёмника, хранить аудит операций и доставлять push адресно. P2P это надёжно не закрывает на мобильных сетях за CGNAT. Поэтому — минимальный управляемый backend; это же совпадает с проверенным дизайном оригинала.

### Что реализуем в прототипе (стек)

- **Backend:** Node.js + Express, хранилище SQLite (better-sqlite3) — ноль внешних зависимостей для локального запуска. FCM через Firebase Admin SDK (ключ сервис-аккаунта — только на сервере, не в APK). Очередь команд = таблица `commands` (источник истины).
- **Android:** новое приложение (исходники оригинала из APK восстановить нельзя — обфускация), современный стек: Kotlin, minSdk 24 / target 34, Android Views + ViewBinding, корутины, Retrofit/OkHttp, FCM, foreground-сервис `phoneCall`, `TelecomManager.placeCall`. Одно приложение, две роли: **Контроллер (A)** и **Приёмник (B)**.
- **Локальный тестовый режим:** по умолчанию B выполняет **безопасный тестовый обработчик** (журнал + уведомление + статус `CALL_SIMULATED`), а не настоящий звонок. Реальный вызов включается явным переключателем и только для номера из allowlist.

### Конечный автомат операции

`CREATED → AUTHORIZED → DISPATCHED → RECEIVED → CALL_REQUESTED → COMPLETED` + ветки ошибок/таймаутов: `EXPIRED`, `REVOKED`, `DUPLICATE_IGNORED`, `NOT_ALLOWED`, `DEVICE_OFFLINE`, `CALL_BLOCKED`, `ERROR`. Каждая команда — уникальный `commandId` (UUID) + `nonce` + `expiresAt`; повторная доставка того же `commandId` на B не инициирует второй звонок (идемпотентность по локальной записи обработанных id).

### Безопасность (из ТЗ п. 10)

- Токен устройства (Bearer) на каждый запрос; TLS; серверная проверка пары A↔B и права «инициировать открытие».
- Серверные секреты (ключ Firebase Admin) — только на сервере, в APK их нет.
- Номер шлагбаума хранится на B, сервер хранит только идентификатор/метку; B сверяет номер с локальным allowlist.
- В журналах нет токенов/секретов/одноразовых кодов.
- B принимает только команду «позвонить на разрешённый номер шлагбаума», ничего больше.
