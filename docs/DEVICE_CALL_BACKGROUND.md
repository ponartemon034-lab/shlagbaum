# Звонок на телефоне B в фоне и при заблокированном экране: механизм и ограничения Android

Это разбор ключевого требования ТЗ (п. 4, 8): телефон B должен инициировать исходящий вызов на номер шлагбаума, **даже если его экран заблокирован**, по команде из интернета. Ниже — как это сделано, что гарантируется, а что зависит от устройства.

## Как реализовано (совпадает с проверенным приёмом оригинала)

1. **Доставка-будильник.** Команда приходит на B одним из двух путей:
   - **FCM data-push с `priority=high`** (продакшен) — будит приложение даже из Doze и при выгрузке из памяти; это основной надёжный способ (как в оригинале);
   - **резервный опрос очереди** (`CommandPollService`) — работает, пока сервис жив; хорош для локального теста и короткой блокировки.
2. **Foreground-сервис типа `phoneCall`.** Приём команды немедленно поднимает `OpenCallService` с `startForeground(..., FOREGROUND_SERVICE_TYPE_PHONE_CALL)`. Это разрешённый на Android 14 способ выполнять телефонную операцию из фона.
3. **Инициирование вызова через `TelecomManager.placeCall()`** с разрешением `CALL_PHONE` и выбором SIM через `PHONE_ACCOUNT_HANDLE`. Это **не** `ACTION_CALL` Activity (которую нельзя запустить из фона) и **не** требует роли дозвонщика по умолчанию или Accessibility.

Почему это работает при заблокированном экране: вызов ставится системным Telecom-сервисом, которому не нужен передний план приложения; экран может оставаться выключенным/заблокированным.

## Что гарантируется, а что — нет (честно)

| Аспект | Статус |
|---|---|
| Инициирование вызова из фона/с локскрина при доставленной команде | **Работает** штатными средствами (подтверждается тем, что оригинал делает так же). Проверка на реальных устройствах у меня не выполнена — физических телефонов нет. |
| Пробуждение из глубокого Doze при экране выключенном на минуты и выгруженном приложении | Надёжно — **только через высокоприоритетный FCM**. Опрос (pull) в этом случае не гарантирует пробуждение. |
| Доставка на устройствах без Google Play Services (без GMS) | FCM недоступен → остаётся только pull с его ограничениями. |
| Автозапуск/выживание сервиса на оболочках Xiaomi/Huawei/Oppo/Vivo/Samsung | Зависит от OEM. Нужны ручные настройки: автозапуск, «не экономить батарею», «не ограничивать фоновую активность». См. инструкцию в INSTALL.md. |
| Старт после перезагрузки | `BootReceiver` перезапускает опрос, если приёмник был включён (и ОС доставила BOOT_COMPLETED — некоторые OEM задерживают/не шлют до разблокировки). |
| Подтверждение, что шлагбаум **открылся** | **Невозможно** из факта звонка. Приложение знает только, что вызов инициирован, и честно показывает статус вызова, а не «открыто». |

## Что мы НЕ делаем (границы безопасности, ТЗ п. 8, 10)

- Не запрашиваем роль дозвонщика по умолчанию, Accessibility Service, SYSTEM_ALERT_WINDOW ради обхода ограничений фона.
- Исключение из оптимизации батареи запрашивается **явно, с пояснением**, и только на телефоне B.
- B звонит **только** на номер из локального allowlist, соответствующий `barRef` из авторизованной команды. Удалённое управление произвольными телефонными функциями не реализуется.

## Ограничения фонового запуска и способы проверки

- **Ограничение запуска Activity из фона** (Android 10+): мы его не используем — вместо Activity поднимается foreground-сервис. Это и есть обход проблемы «из фона нельзя открыть экран».
- **Doze / App Standby buckets:** при простое доставка pull замедляется; FCM high-priority имеет временное исключение из Doze. В команду включён `expiresAt`, чтобы «проснувшаяся с опозданием» просроченная команда не звонила.
- **Дедупликация:** один `commandId`; повторная доставка того же id на B игнорируется (локальный список обработанных) и на сервере (идемпотентность) — двойного звонка не будет.

**Как проверить** (нужны реальные телефоны — см. TWO_DEVICE_TEST.md): сценарии с выключенным на несколько минут экраном, с выгруженным приложением, после перезагрузки, при временной потере интернета, при повторной доставке и при просроченной/отозванной команде.
